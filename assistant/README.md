# TodoDay AI 助手（企业微信）

在企业微信里对助手说一句计划，助手把它记进 TodoDay 的任务列表。

```
你：明天下午三点跟老王开会，重要
助手：已记录：
      跟老王开会
      2026-10-16 周五 · 工作 · 高优先级
```

## 为什么是「自建应用」而不是「群机器人」

**群机器人的 webhook 是单向的**：`cgi-bin/webhook/send?key=xxx` 只能往里推消息，没有任何接收入口，监听它只会得到 405 或超时。要能收到你发的消息，必须用**自建应用的「接收消息」回调**。

这条差别决定了整个接入方式，先记下来能省很多时间。

## 目录

```
assistant/
  cmd/assistant/main.go        入口：读配置、起服务、优雅退出
  internal/config/             配置读取与启动校验
  internal/wecom/              签名校验、AES 加解密、回调处理、主动发消息
  internal/parse/              Kimi 解析 + 规则兜底
  internal/todoclient/         调用 TodoDay 后端的 HTTP 客户端
  internal/bot/                编排：解析 → 建任务 → 回复
  .env.example                 全部配置项示例
```

## 它是怎么工作的

```
企业微信服务器
   │  POST 加密 XML
   ▼
/wecom/callback ── 校验签名、解密、验证 receiveid（微秒级）
   │  立刻回 "success"
   │
   └─→ 后台 goroutine
         ├─ 解析（Kimi，失败则规则解析）
         ├─ 建任务（HTTP 调 TodoDay 后端，clientId 幂等）
         └─ 主动推送回执
```

**为什么不用「被动加密回复」**：那要求 5 秒内返回，超时企业微信会重投 3 次。而解析一句话要调 AI，耗时不可控。所以回调里只做解密（极快）并立刻回 `success`，剩下的异步做、异步回。

**重复投递怎么办**：用企业微信的 `MsgId` 作为建任务的 `clientId`（前缀 `wx_`）。后端对相同 `clientId` 返回既有任务而不新建，所以即便重投也不会出现两条任务。另外进程内有一份 `MsgId` 缓存，重投时不会再跑一遍解析、也不会重复回复。

## 配置

复制 `.env.example` 为 `.env` 填写。**本服务不读 `.env` 文件**，只读进程环境变量——用 `export $(grep -v '^#' .env | xargs)` 导入，或写进 systemd / docker 的环境配置。

| 变量 | 默认 | 机密 | 说明 |
| --- | --- | :---: | --- |
| `ASSISTANT_ADDR` | `:8090` | | 本服务监听地址 |
| `WECOM_CORP_ID` | 必填 | | 企业 ID，同时用于校验回调的 `receiveid` |
| `WECOM_AGENT_ID` | 必填 | | 自建应用 AgentId |
| `WECOM_SECRET` | 必填 | ✅ | 应用 Secret，用于换取 access_token |
| `WECOM_TOKEN` | 必填 | ✅ | 回调 Token（自己填的） |
| `WECOM_ENCODING_AES_KEY` | 必填 | ✅ | 回调密钥，固定 43 个字符 |
| `TODO_API_BASE` | `http://127.0.0.1:8080` | | TodoDay 后端地址 |
| `TODO_USERNAME` | 必填 | | 用于登录的账号 |
| `TODO_PASSWORD` | 必填 | ✅ | 该账号密码 |
| `TODO_WORKSPACE_ID` | 必填 | | 目标工作区 ID |
| `KIMI_API_KEY` | 空 | ✅ | 留空则全部走规则解析 |
| `MOONSHOT_API_KEY` | 空 | ✅ | 同上，别名键 |
| `KIMI_BASE_URL` | `https://api.moonshot.cn/v1` | | Moonshot 的 OpenAI 兼容地址 |
| `ASSISTANT_MODEL` | `moonshot-v1-8k` | | 解析用模型 |
| `PARSE_TIMEOUT` | `8s` | | AI 调用超时 |

必填项缺失时启动即失败，并列出**缺了哪些键名**（不含值）。

`TODO_WORKSPACE_ID` 怎么拿：登录网页版后看 `GET /api/me` 返回的 `workspaces[].id`。

## 企业微信后台配置

1. **拿企业 ID**：管理后台 → 我的企业 → 企业信息 → 企业 ID。
2. **建自建应用**：应用管理 → 自建 → 创建应用。记下 **AgentId** 和 **Secret**。
3. **设可见范围**：把要给助手发消息的成员加进应用的可见范围，否则他们发不了消息、也收不到回执。
4. **配回调**：应用详情 → 接收消息 → 设置 API 接收：
   - **URL**：`https://你的域名/wecom/callback`
   - **Token**：自己随便定一串，填进 `WECOM_TOKEN`
   - **EncodingAESKey**：点「随机获取」，填进 `WECOM_ENCODING_AES_KEY`
5. 点保存。企业微信会立刻发一个 GET 请求验证，服务必须当时在跑。

**回调地址必须是公网可达的 HTTPS**。企业微信是云端主动推消息，没有长连接或轮询模式——你的服务必须能被它的服务器直接访问到。内网穿透或反向代理由你自己准备，本项目不含这部分。

**可信 IP**：如果推送回执时报 `60020` 错误，说明需要把出口 IP 加进「企业可信 IP」列表。

## 运行

```bash
cd assistant
export $(grep -v '^#' .env | xargs)
go run ./cmd/assistant
```

启动时会先登录 TodoDay 后端并确认账号属于目标工作区——配错在这里就报错，而不是等第一条消息进来。

### 本地自测回调握手

不需要真实企业微信后台，生成一条合法的验证请求：

```bash
go run ./cmd/assistant -print-handshake
```

它会打印一条 `curl` 命令，直接执行即可看到返回明文 `test-echo`。这验证了签名与解密链路是通的。

> `echostr` 是 base64，含 `+` `/` `=` 三个在 query string 里有特殊含义的字符（其中 `+` 会被解析成空格），所以地址是经 URL 编码拼出来的。手工拼字符串做这个自测会必然失败，并把你引向错误的排查方向。

### 不开企业微信也能验证配置

`-record-test` 会跳过企业微信，直接把一句话按「解析 → 建任务」跑一遍，然后退出：

```bash
go run ./cmd/assistant -record-test "明天 交周报 #工作 !!!"
```

输出示例：

```
已记录：交周报 ｜ 日期 2026-10-16 ｜ 分组 工作 ｜ 优先级 1（解析来源：rule）
```

这是**配回调之前**确认凭据、工作区与解析链路是否正常的推荐方式。配置错误会直接报出来，并且指向该改哪个变量：

| 现象 | 含义 |
| --- | --- |
| `无权访问该工作区：账号不属于工作区 N` | `TODO_WORKSPACE_ID` 填错了 |
| `登录被拒绝：状态码 401` | `TODO_USERNAME` / `TODO_PASSWORD` 填错了 |
| `缺少必填配置：A、B` | 列出所有缺失的键名（不含值） |
| `连接后端失败：…` | `TODO_API_BASE` 不对，或后端没起 |

## 测试

```bash
cd assistant
go test ./... -count=1
```

覆盖内容：

- **加解密**：用**企业微信官方的回调测试参数**验证签名与解密（不是只做自己加密再自己解密的往返——那只能证明自洽，证明不了和微信服务器一致）；另覆盖填充边界、错误密钥、`receiveid` 不匹配、非法密文。
- **回调**：构造合法密文走完整的 `httptest` 请求，断言 GET 返回**明文** echostr、POST 秒回 `success` 且消息被交给处理器；签名错误、外来 CorpID、非文本消息各有断言。
- **解析**：表驱动覆盖中英文相对日期、绝对日期、`#分组`、三档优先级、闰年、时区差异、非法日期。
- **编排**：重复投递去重、空消息、解析失败、记录失败、降级提示、发送失败。

## 未实现（如实列出）

- **不包含部署**：没有 Dockerfile、systemd 单元、CI，也不做内网穿透。
- **不做查询/完成/删除/统计**：一条消息就是「记一条任务」。想查今天有什么、标记完成，目前只能开网页。
- **固定单工作区**：所有消息记进配置里那一个工作区，不支持多人各自记自己的。要支持得先有账号绑定流程。
- **无持久化队列**：回执在内存里排队，进程重启会丢掉未发出的一部分（任务本身已落库，不会丢）。
- **不做多轮对话**：一句话解析不出内容时只提示重说，不会追问。
- **非文本消息**（图片/语音/文件）一律忽略。
- **没有针对真实企业微信的端到端验证**：仓库里的测试覆盖了加解密与编排逻辑，但签约、保存回调、真实推送这几步需要你的企业凭据与公网地址，必须实测一次才算接通。

## 一个已核实的细节

企业微信的填充用的是 **32 字节块**（官方 `PKCS7Encoder` 的 `BLOCK_SIZE = 32`），不是 AES 的 16 字节块；`EncodingAESKey` 需要补一个 `=` 才能 base64 解码；IV 取密钥前 16 字节；明文尾部带 `receiveid`（自建应用为 CorpID），必须校验。这几点任一搞错都会表现为「后台保存回调地址时提示不通过」，而错误信息不会告诉你是哪一步。
